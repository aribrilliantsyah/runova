# Bagian 7: deviasi dan keputusan

Nama, signature, dan konstanta di blok Interfaces rencana tidak diubah. Hal-hal di bawah adalah tambahan atau koreksi.

## Koreksi terhadap rencana

1. **`include_dir pg_hba.d` tanpa tanda kutip.** Rencana menulis `include_dir 'pg_hba.d'`. Di `pg_hba.conf` tanda kutip tunggal bukan sintaks (berbeda dengan `postgresql.conf`): PostgreSQL mencari folder bernama `'pg_hba.d'` dan gagal start (`could not open configuration directory "…/'pg_hba.d'"`, ditemukan di e2e lokal). Installer menulis `include_dir pg_hba.d` (relatif terhadap folder `pg_hba.conf`) dan mengenali bentuk tanpa/dengan tanda kutip ganda agar tidak menambah dua kali. Spec §7 masih menulis tanpa kutip.
2. **Paket tambahan `jq` dan `curl`** (selain `docker.io caddy postgresql-18 ufw`), dari apt Ubuntu yang sama: `jq` untuk menggabungkan `daemon.json`, `curl` untuk menunggu panel menjawab. Keduanya biasanya sudah ada di Ubuntu Server.
3. **Urutan langkah** di `run_steps`: paket → user/folder → binary → kunci → env → Docker → Caddy → PostgreSQL → alamat panel → admin → ufw → unit → `runova check`. Admin dibuat **sebelum** layanan menyala agar `ReconcileRoles` saat start langsung memberi admin role PostgreSQL. Binary disalin lebih dulu karena `keygen`, `admin`, dan `panel set` memakainya.
4. **`runova admin exists`** (tambahan, exit 0/1; 2 untuk galat): dipakai installer agar `admin create` hanya jalan sekali. Pemasangan ulang tanpa `--domain/--port` mengandalkannya juga: bila admin sudah ada, alamat panel tidak diubah; bila belum, bawaan `--port 8443`.
5. **`runova panel set --public-ip`** boleh berdiri sendiri atau bersama `--domain`/`--port`; tidak menyentuh alamat panel bila dipakai sendiri.
6. **`runova check`** memeriksa: Docker, `docker-init` (dicari di `PATH` dan `/usr/libexec/docker`, `/usr/lib/docker`, dll.; catatan post-merge-fixes #7), Caddy admin, PostgreSQL (versi), `secret.key`, folder data (bisa ditulis), dan folder `pg_hba.d`. Format `ok <nama> <detail>` / `fail <nama>: <alasan>`. Penting: pemeriksaan dijalankan sebagai user `runova` oleh installer, jadi sekaligus membuktikan izin folder.
7. **Berkas `runova.service`**: ditambah `Description`, `RestartSec=3`, `[Install] WantedBy=multi-user.target`. Isi lain persis seperti Global Constraints.
8. **Caddyfile bawaan paket dikenali lewat `dpkg-query -W -f='${Conffiles}'`** (md5 conffile) bukan `/var/lib/dpkg/info/caddy.md5sums` (berkas itu tidak memuat conffile: dicek pada paket `caddy 2.6.2-14` di Ubuntu 26.04). Caddyfile yang sudah berisi persis `{ admin localhost:2019 }` juga dianggap beres. Drop-in `caddy.service.d/runova.conf` mengganti `ExecStart` menjadi `caddy run --environ --resume --config /etc/caddy/Caddyfile`; Caddy di-restart hanya bila Caddyfile atau drop-in berubah.
9. **ufw**: port SSH dibaca dari `sshd -T`, ditambah `ss` dan `ssh.socket` (socket activation di Ubuntu); semua port diizinkan sebelum `ufw --force enable`, dan `enable` hanya bila status `inactive`.
10. **`daemon.json`**: bila sudah punya `default-address-pools` sendiri, dibiarkan dengan peringatan (tidak ditimpa, tidak digabung ke daftar pengguna). Docker di-restart hanya bila berkas berubah. `daemon.json` rusak menghentikan installer.
11. **LICENSE**: rencana mensyaratkan berkas `LICENSE` di arsip, tetapi proyek belum punya lisensi. Dibuat `LICENSE` berisi "all rights reserved" yang konservatif; **pemilik perlu menggantinya** dengan lisensi pilihannya sebelum rilis publik.
12. **Folder baru `/etc/postgresql/18/main/pg_hba.d`** dimiliki `postgres:runova` 0770; file awal `runova.conf` hanya ditulis bila belum ada (Runova menimpa isinya sendiri lewat `WriteHBA`, dan pemasangan ulang tidak menghapus jaringan yang ditambahkan admin).
13. **`scripts/release.sh`** menerima versi `X.Y.Z[-sufiks]`, arsip deterministik (`--sort=name --mtime=@0`), `SHA256SUMS` di dalam arsip (untuk 4 file lain) dan `dist/SHA256SUMS` (untuk arsip).

## E2E lokal

14. **Flag dev `RUNOVA_DEV_CHMOD=1`** (`config.Config.DevChmod`): `Chown` diganti `chmod 0777` agar proses non-root bisa menyiapkan folder `/data` container. Ditolak (exit 1) bila `RUNOVA_DATA` = `/var/lib/runova` atau alias-nya (pola `RUNOVA_FAKE_BACKENDS`, logika `os.SameFile` dipakai bersama lewat `onProductionData`).
15. **PostgreSQL e2e** (`postgres:18`, `--network host`, port **55432** karena 5432 sering terpakai di mesin dev): `hba_file` kustom di-mount ke container dengan `include_dir hba.d`; `hba.d` adalah folder host yang ditulis Runova lewat `RUNOVA_PG_HBA` (`WriteHBA` jalan nyata), dan `pg_reload_conf()` nyata (role `runova` mendapat GRANT yang sama seperti installer). Role `runova` masuk lewat TCP + password (`RUNOVA_PG_DSN`). Container aplikasi menjangkaunya lewat `host.docker.internal:55432` — `ExtraHosts host-gateway`, dengan `listen_addresses=*` dan subnet `172.30.0.0/16` di `runova.conf`. `PGPORT` di env aplikasi mengikuti port dari DSN (`dbs.Service.PGPort`).
16. **Caddy e2e**: `caddy:2`, `--network host`, `caddy run --resume`, volume bernama (dihapus oleh `down`). Panel mode IP di `:8443` lewat Caddy dengan sertifikat internal (dicek `curl -k`).
17. **Aplikasi contoh `test/e2e/hello`** punya dua endpoint tambahan di luar rencana (`/connect?dsn=` dan `/dial?addr=`) yang dipakai skenario `isolation` untuk menguji dari **dalam** container budi (bukan dari host). Skenario itu memakai kontrol positif lebih dulu (budi bisa membuka `budi_app` dan menjangkau host) sehingga penolakan berarti isolasi, bukan salah konfigurasi.
18. **Isolasi database** diuji di tingkat PostgreSQL: budi ditolak di `andi_app` dengan `permission denied` (hak `CONNECT` dicabut dari `PUBLIC`); isolasi jaringan: IP container andi tidak terjangkau dari jaringan `runova-u<id>` budi.
19. **Pembersihan `down`**: menghapus container berlabel `runova.app`, container stack, jaringan `runova-u*`, volume Caddy, dan folder state (file milik UID container dihapus lewat container `ubuntu:26.04` bila perlu), lalu gagal bila masih ada container berawalan `runova-`. `up` yang gagal di tengah membersihkan dirinya sendiri; `up` kedua tanpa `down` ditolak. `run.sh` butuh stack yang baru dinaikkan (admin dibuat oleh skenario 1).
20. **JAR contoh** `testdata/hello-spring` (Bagian 2) dibangun di `maven:3-eclipse-temurin-21` memakai `~/.m2` terpisah di `test/e2e/.cache/m2`, hasilnya di-cache di `test/e2e/.cache/hello-spring.jar`. JAR itu butuh env `DB_URL`; skenario mengisinya dengan nilai uji.
21. **Pengujian installer**: `test/bats.sh` membangun image kecil (`test/Dockerfile.bats`: `bats/bats` + `jq`) dan menjalankan `shellcheck` untuk semua skrip. Stub di `test/fixtures/bin` mencatat panggilan ke `$CALLS`. `runuser` palsu hanya mencatat nama pengguna; kepemilikan sungguhan (`chown`/`runuser` oleh root) tidak bisa diuji di sini.

## Belum teratasi / tidak teruji

- **Installer belum dijalankan di Ubuntu 26.04 sungguhan** (tanpa VM sesuai keputusan user). Diverifikasi terhadap paket sungguhan di container `ubuntu:26.04`: `docker.io 29.1.3` memuat `/usr/bin/docker-init`, `caddy 2.6.2` memiliki conffile `/etc/caddy/Caddyfile`, dan `postgresql-common` menambah `include_dir 'conf.d'` otomatis (sehingga `conf.d/runova.conf` terbaca). Belum teruji: `apt-get install` utuh, `systemctl`, `ufw` nyata, urutan start saat boot, aturan Docker-vs-ufw.
- Caddy di Ubuntu 26.04 adalah **2.6.2**. Koordinator mengganti image e2e menjadi `caddy:2.6.2` (bisa diubah lewat `CADDY_IMAGE`) dan menjalankan ulang e2e: kedelapan skenario lulus (deploy tanpa jeda 156 permintaan, 0 gagal), jadi konfigurasi JSON Bagian 4 terbukti jalan di 2.6.2.
- Pada Caddy 2.6.2, `caddy.service` bawaan paket memakai `Type=notify`; drop-in mengganti `ExecStart` saja.
- Image `eclipse-temurin:21-jre` ditarik saat deploy pertama (`docker pull`): server tanpa akses internet tidak bisa mendeploy JAR sampai image ada.
