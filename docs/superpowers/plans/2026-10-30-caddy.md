# Runova Bagian 4: Caddy, Domain, dan Deploy Tanpa Jeda — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Aplikasi bisa dibuka lewat domain dengan HTTPS otomatis dan lewat `IP:port` (on/off), panel sendiri bisa diakses lewat domain atau `IP:port`, dan deploy tanpa jeda menjadi bawaan.

**Architecture:** `internal/caddy` membangun **seluruh** konfigurasi JSON Caddy dari keadaan di SQLite (fungsi murni `Build`) dan mengirimnya ke admin API dengan `POST /load`. Tidak ada patch parsial: setiap perubahan = bangun ulang + load, sehingga Caddy selalu sama dengan DB. Sinkronisasi diserialkan oleh satu goroutine `Syncer` yang menerima sinyal "kotor" dan juga memeriksa tiap 30 detik apakah Caddy restart (konfigurasi kosong → load ulang).

**Tech Stack:** Go stdlib (`net/http`, `encoding/json`, `crypto/tls`), Caddy 2 dari apt Ubuntu.

**Spec:** `docs/spec.md` §2, §5 (akses IP, deploy), §6.

**Bergantung pada:** Bagian 1, Bagian 3 (`apps.Service`, `store.App`, deploy).

## Global Constraints

- Admin API Caddy: `http://127.0.0.1:2019` (dapat diganti `RUNOVA_CADDY_ADMIN`). Header `Origin` tidak dikirim.
- Server `runova-https`: listen `:80`, `:443`, satu route per host (domain aplikasi dan domain panel). HTTPS otomatis Caddy (redirect HTTP→HTTPS) aktif untuk server ini.
- Server `runova-ip-<port>` per aplikasi dengan akses IP nyala: listen `:<ip_port>`, `automatic_https.disable: true`, satu route tanpa matcher host → `127.0.0.1:<host_port>`.
- Server `runova-panel-ip` bila panel mode IP: listen `:<panel_port>`, `tls_connection_policies` dengan sertifikat internal (`issuers: [{"module":"internal"}]`, subject = IP publik bila diisi), → `RUNOVA_LISTEN`.
- Semua route reverse_proxy menambah header `X-Forwarded-Proto` / `X-Forwarded-For` (bawaan Caddy) — Runova membaca keduanya hanya dari loopback (Bagian 1). **Jangan** mengisi `trusted_proxies`: Caddy harus menimpa XFF dengan alamat asli klien, karena throttle login memakai elemen pertama XFF (temuan review Bagian 1).
- Domain: huruf kecil, label `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$`, minimal dua label, total ≤ 253, tidak boleh IP, tidak boleh sama dengan domain panel, unik di server, maks 5 per aplikasi. Wildcard tidak didukung.
- Deploy tanpa jeda (`deploy_mode = 'zero'`) jadi bawaan untuk aplikasi baru; aplikasi lama tetap pada mode yang tersimpan.
- Status domain: `pending` (belum ada sertifikat), `active`, `error` (dengan pesan); dicek saat domain ditambah lalu tiap 5 menit sampai `active`.

## Review Focus

- **Caddy di-restart / server reboot** → dalam ≤ 30 detik route dimuat ulang tanpa campur tangan. Test di Task 2 (`TestSyncerReloadsAfterCaddyRestart`).
- **Load ditolak Caddy (konfigurasi salah)** → perubahan domain di DB di-rollback dan pengguna mendapat 502 "Caddy menolak konfigurasi: …", bukan domain "aktif" palsu. Test di Task 3 (`TestAddDomainCaddyRejects`).
- **Domain sudah dipakai pengguna lain atau sama dengan domain panel** → 409 tanpa menyebut pemiliknya. Test di Task 3 (`TestDomainUniqueness`).
- **Deploy tanpa jeda gagal sehat** → lalu lintas tetap ke container lama, container baru dihapus, aplikasi tetap `running` (bukan `failed`), notifikasi tetap dikirim. Test di Task 4 (`TestZeroDowntimeFailureKeepsOld`).
- **Port host lama dan baru saat transisi** → container baru memakai host port berbeda; setelah alih, port lama dibebaskan dan dapat dipakai ulang. Test di Task 4 (`TestZeroDowntimeSwitchesUpstream`).
